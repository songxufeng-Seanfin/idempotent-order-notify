订单通知的幂等消费与乱序处理 · 技术文档

版本：v1.0 · 2026-11-16
项目：idempotent-order-notify
仓库：https://github.com/songxufeng-Seanfin/idempotent-order-notify
运行环境：Python 3.13.14 · Django 5.2.19 · SQLite 3 · 可选 Redis Stream
代码规模：26 个文件、约 1,840 行（含模板与测试）、6 张业务表、19 个自动化测试

这份文档从看板上的按钮写起，再到请求怎么走、Django 怎么调度，最后拆到数据、状态机、并发与队列。没学过消息队列也能读，用到的词都在第一次出现时解释了。

1. 项目概览

1.1 要解决什么问题

电商/交易系统里，订单状态变化通常以「通知」（也叫事件，Event：一件事发生后发出的一条消息）的形式在系统之间传递，例如「订单已支付」「包裹已发货」。真实环境有两条几乎必然发生的干扰：

  • 重复投递（at-least-once delivery，至少投递一次）：消息队列为了保证消息不丢，网络抖动、消费者超时、未确认都会让同一条消息再投一次。如果消费端不做防护，用户会收到两条短信、积分会被加两次。
  • 乱序到达（out-of-order）：多个生产者、多个分区、重试队列都会让「发货」比「下单」先到。如果收到什么就写什么，订单状态会跳步甚至回退。

本项目用一个可交互的演示系统，把这两类异常故意制造出来，再验证系统在三个层面都不出错：订单状态正确、对外通知不重复、状态绝不回退。

2. 第一层：从屏幕到服务器

打开 http://127.0.0.1:8000/，看到的是一个演示控制台（Console）。它只有两类交互：

  1. GET / — 渲染看板。视图 notify/views.py :: console() 查 6 个统计数字、最近 12 笔订单、最近 40 次消费尝试、最近 12 条通知、最近 20 条状态流水，交给 templates/console.html 排版。
  2. POST /run/<场景>/ — 点击按钮触发。notify/views.py :: run_scenario_view() 调 consumer.run_scenario() 真的跑一遍流水线，然后用 PRG（Post/Redirect/Get：提交后重定向，避免刷新重复提交） 跳回看板，顶部显示一行汇总。

这里可以复习一条对所有 Web 系统都成立的规律：页面不会自己变。每点一次按钮，浏览器发一次请求，服务器跑一圈，再把新结果送回来画成页面。

405 Method Not Allowed（路找到了但请求方式不对）在这里也有实例：/run/reset/ 只允许 POST，用 GET 直接访问会被 @require_POST 装饰器拒掉，测试 ConsoleTests.test_get_not_allowed 专门验证了这一条。

一个刻意的设计：状态机与队列是解耦的。state_machine.py 是纯函数，不 import 任何模型；queue.py 只负责消息进出，不知道订单有几种状态。consumer.py 把两者粘起来。这样换队列（DB → Redis → Kafka）时，状态规则一行都不用改。

5. 第四层：数据模型（6 张表）

表作用关键约束
Order订单当前状态order_no 唯一；state_mask 位图；version 状态版本
NotifyEvent事件表 / 队列消息event_id 唯一（幂等的锚点）；delivered、claimed_by、claimed_at 模拟投递状态；delivery_count 记累计投递次数
ProcessedEvent消费结果（幂等闸门）event_id 唯一 + source_event 一对一；duplicate_hits 记重复被拦次数
DeliveryAttempt每一次消费尝试无唯一约束，重复被拦也留一条；看板时间线的数据源
NotificationLog对外通知（副作用）event_id 唯一，保证同一事件最多发一条
StateTransition状态变更流水每次位图前进记一条 from_mask → to_mask

5.1 为什么需要两张「结果表」

这是本项目最容易混淆、也最值得记住的一点：

  • ProcessedEvent 一个 event_id 只有一条，它的存在本身就是「这条处理过了」的凭证，负责正确性。
  • DeliveryAttempt 来几次记几条，负责可观测性：重复投递被拦下、乱序暂存、重放了几条，都要看得见。

第一版只做了 ProcessedEvent，结果「重复拦下」在看板上永远是 0——被拦下的请求没有留痕。补上 DeliveryAttempt 之后，看板才能显示「1 次生效 + 3 次被拦」。这个坑记在本文第 13 章。

5.2 为什么唯一索引比 if 判断可靠

代码里「先查有没有、再插入」在并发下会失效：两个线程可能同时查到「没有」，然后都插入。数据库的 唯一索引（Unique Constraint） 由存储层保证，任何并发交错下都只会有一行成功。所以本项目把 event_id 唯一作为最后一道防线，代码里的判断只是为了让错误提示更友好。

6. 第五层：状态机与位图

6.1 位图怎么表示进度

定义在 state_machine.py :: STAGES：

阶段事件类型二进制位十进制值业务序号
已创建created第 0 位11
已支付paid第 1 位22
已发货shipped第 2 位43
已完成completed第 3 位84
已取消cancelled第 4 位16—

Order.state_mask = 15 即 01111：四个正常阶段全到了。若 01011，说明「已完成 + 已支付 + 已创建」到了，缺「已发货」——缺哪一步用一个整数直接算出来，不用存四个布尔字段、也不用查历史记录。

6.2 前置校验

required_before(event_type) 返回「这件事发生之前必须已经点亮的所有位」：

  • created → 0（不需要前置）
  • paid → 1
  • shipped → 3（1|2）
  • completed → 7（1|2|4）

can_apply(event_type, mask) 返回三元组 (是否可推进, 原因, 是否属于乱序)。关键分支：

  • 该位已点亮 → 该阶段已到达（重复事件），拒绝
  • 前置位不齐 → 前置阶段未齐：已创建、已支付… 并标记 out_of_order=True，暂存
  • 订单已完成还想取消 → 订单已完成，不允许取消，拒绝
  • 合法 → 按序推进

next_mask() 用 mask | bit 做按位或。或运算只能把 0 变 1，不能把 1 变 0，这就是「状态只前进、绝不回退」在数学上的保证，比在代码里写一堆 if 更可靠。

7. 第六层：一次消费的完整链路

以「同一条 paid 消息被投了两次」为例，走 notify/consumer.py：

步函数动作
1publish_event()NotifyEvent.objects.get_or_create(event_id=...)；重复投递不新建行，只累加 delivery_count
2queue.publish()把 event_id 放进队列（DB 后端把 delivered 置回 False；Redis 后端 XADD）
3consume_pending()claim() 认领一批 → 逐条 consume_one() → 逐条 ack()
4_consume_one_inner()transaction.atomic() 内锁订单行；抢写 ProcessedEvent
5幂等闸门IntegrityError（唯一约束冲突）→ 返回 DUPLICATE，累加 duplicate_hits，不产生任何副作用
6can_apply()合法才 next_mask()；缺前置则写 BUFFERED 返回
7_apply_stage()更新位图与版本、NotificationLog.get_or_create(event_id=...)、StateTransition.create(...)
8_drain_buffer()按业务序号扫描暂存的事件，能推进的全部重放，循环直到一轮没有新增
9consume_one() 包装层无论结果如何，写一条 DeliveryAttempt 审计记录
10queue.ack()标记 delivered=True / XACK，队列不再重投

副作用只发一次的根本原因不是「我们判断了重复」，而是 NotificationLog.event_id 有唯一约束：就算闸门被绕过，get_or_create 也不会插进第二条。

8. 双后端队列

queue.py 定义统一契约，业务逻辑只依赖四个方法：

class EventQueue:
    def publish(self, event_id): ...       # 投递
    def claim(self, consumer, count): ...  # 认领（认领后未确认 = Pending）
    def ack(self, event_id): ...           # 确认
    def pending_count(self): ...           # 还有多少条没确认
语义DatabaseQueue（默认）RedisStreamQueue（可选）
投递delivered=False，delivery_count + 1XADD stream * event_id <id>
认领取 delivered=False 的前 N 条，写 claimed_by/claimed_atXREADGROUP GROUP g c STREAMS key 0（先读 Pending）再读 >
确认delivered=TrueXACK stream group <msg-id>
未确认数filter(delivered=False).count()XPENDING 返回 pending
重投重复 publish 把消息重新置为未确认消费组未 ACK 的消息留在 Pending，换消费者重新读到

get_queue() 读 NOTIFY_BACKEND 环境变量，值为 redis 时尝试连接并 PING；任何异常都自动回退到数据库队列并在看板上标注原因，保证没有 Redis 的机器上演示不会中断。

tests.py :: FakeRedis 是一个内存版 Redis，只实现这六个命令，让 Stream 路径在没装 Redis 的环境里也能被真实测试覆盖（包括「消费者崩溃不 ACK → 消息重投 → 幂等拦下」这条经典场景）。

9. 乱序处理：为什么是「暂存 + 重放」

面对乱序，常见三种做法：

做法问题
收到就写状态跳步，completed 先到会让订单「已完成但没创建过」
直接丢弃迟到的事件消息永久丢失，最终状态不完整
暂存 + 补齐后重放（本项目）既不丢也不硬写，最终状态与按序到达完全一致

_drain_buffer() 用 while 循环反复扫描 BUFFERED 记录，直到某一轮没有任何新增。这是必要的：completed → shipped → paid → created 全部乱序到达后，created 补齐会连锁解锁 paid、shipped、completed 三条，一次扫描不够。每条重放都会写状态流水并标记 replayed=True，看板上能直接看到「顺带重放 3 条暂存事件」。

demo_notify --scenario outoforder 的输出就是这套逻辑的实证：前三条都是 BUFFERED，最后一条 created 到达时位图从 0 → 15，通知恰好补齐到 4 条。

10. 并发与事务

  • consume_one() 整体包在 transaction.atomic() 里，并对 Order 行用 select_for_update() 加行锁，避免两个消费者同时读写同一订单的位图。
  • 抢占 ProcessedEvent 时再套一层 transaction.atomic() 作为保存点（savepoint）：捕获 IntegrityError 只回滚这一小段，外层事务不会变成 broken 状态。
  • SQLite 下 select_for_update 是空操作，但唯一索引依然生效，所以正确性不依赖数据库是否支持行锁；换到 MySQL/PostgreSQL 时代码无需改动。
  • version 字段每次状态前进 +1，是留给后续做乐观锁（Optimistic Locking：更新时校验版本，版本变了就重试）的接口。

把一条订单通知故意投了三次之后，我终于把「幂等」讲明白了

项目：idempotent-order-notify · Django 5.2 · SQLite · 可选 Redis Stream
仓库：https://github.com/songxufeng-Seanfin/idempotent-order-notify
6 张表 · 约 1,840 行代码 · 19 个自动化测试全部通过

前阵子把「闲小集」那个校园二手交易平台做完了，功能闭环、文档博客也补齐了。轮到简历上的第二个项目时，我挑了一个听起来最唬人的：订单通知的幂等消费与乱序处理。

一开始我是有点虚的。「幂等」「乱序」「Redis Stream」「位图状态回滚」——每个词单独查都能看懂，凑在一起就像天书。真正把它做出来之后反而发现：这东西的核心其实一句话就能说完，难的从来不是概念，是把概念变成能跑、能验证、能指着说「你看，它确实没出错」的东西。

这篇就记录我怎么把这句人话，一层层变成代码。

一、先说人话：电梯按钮

幂等（Idempotency）的白话版：同一个操作做 100 次，和做 1 次效果一样。

电梯按钮是最好的比喻。你按一下「8 楼」，灯亮；再按两下，灯还是亮，电梯不会上三层。但如果这是个「下单」按钮、或者一条「订单已支付」的通知，重复两次就可能扣两次钱、发两条短信、加两次积分。

消息队列为什么会重复？因为主流队列为了保证不丢消息，走的是「至少投递一次」（at-least-once）：网络抖一下、消费者处理慢了、确认包丢了，它就再投一次。它不是故意捣乱，是「宁可重复，不可丢失」。所以重复不是异常，是默认前提，幂等必须由消费端自己负责。

乱序（Out-of-order）更好懂：先发生的事反而后到。「发货」通知比「下单」通知先到，收到什么就写什么的话，订单就会出现「已完成但没创建过」这种鬼状态。

所以这个项目要回答的其实只有一个问题：当通知又重复又不按顺序来时，怎么保证订单状态是对的、短信只发一条？

二、第一个念头：加个 if 不就行了？

我最初的直觉是：查一下这个事件处理过没有，处理过就跳过。

if ProcessedEvent.objects.filter(event_id=event_id).exists():
    return "重复了，跳过"
# ...真正处理

这段代码在单线程里跑得好好的，但它是错的。错在「查」和「写」之间有时间差：两个消费者同时查到「没有」，然后都往下走，两边都发了通知。这种 bug 平时不出现，一到并发就冒出来，而且很难复现。

正确的姿势是把判断交给数据库：给 event_id 加唯一索引（Unique Constraint），然后直接抢着插入一条消费记录。谁插进去谁干活，插不进去的会撞上唯一约束冲突，那就是重复消息。

try:
    with transaction.atomic():          # 保存点：局部失败不拖垮整笔事务
        record = ProcessedEvent.objects.create(
            source_event=event, event_id=event_id, result="PROCESSING", ...
        )
except IntegrityError:                  # 唯一约束冲突 = 别人已经处理过了
    return ConsumeResult(event_id, "DUPLICATE", "重复投递被拦下，通知不会重发")

这一下思路就变了：不去「判断」有没有重复，而是让数据库「仲裁」谁有资格处理。代码里的 if 只是让提示更友好，唯一索引才是最后的底线。

我还顺手加了第三道防线：对外通知表 NotificationLog 的 event_id 也是唯一的，用 get_or_create 写。哪怕前面闸门真被绕过，也插不进第二条通知。正确性不依赖每一层都不犯错，而是靠多层兜底。

三、乱序比重复麻烦，因为「丢」和「写」都不对

重复消息可以拦掉，乱序消息不行。

我在 state_machine.py 里给四个阶段各分了一个二进制位：

阶段位值
已创建第 0 位1
已支付第 1 位2
已发货第 2 位4
已完成第 3 位8

一个订单走到「创建 + 支付 + 发货 + 完成」，位图就是 01111（十进制 15）。这个位图（Bitmask）最妙的地方是：缺哪一步可以直接算出来。01011 一眼看得出「已发货」没到。

而且推进状态用的是按位或：

def next_mask(event_type, mask):
    return mask | bit_of(event_type)

或运算只能把 0 变 1，永远不能把 1 变 0。「状态绝不回退」不是我写了一条规矩，是数学上就做不到。 这比堆一堆 if 判断舒服太多。

那「发货」先到怎么办？三条路：

  1. 收到就写 → 状态跳步，错。
  2. 直接丢掉 → 消息永久丢失，订单永远缺一步，错。
  3. 暂存（Buffer）：先记一条 BUFFERED，不推进也不丢；等前置阶段补齐，再按业务序号重放（Replay）。

第三条是唯一能收敛到正确终态的做法。我特意做了个「倒序全投」的场景：completed → shipped → paid → created 依次到达。前三条都被暂存，最后一条 created 到达时，位图从 0 一步变成 15——因为 _drain_buffer() 会连锁把另外三条按序补齐。

这里有个小细节值得记：重放必须循环扫描直到某一轮没有新增。一次扫描只能解锁一条，而这里一次要连锁解锁三条。

四、没有 Redis，怎么办？

简历上写的是「Django + Redis Stream」。但这台机器上既没有 redis-server，也没有 Docker，import redis 都报 No module named 'redis'。

要是直接写死 Redis，项目就跑不起来，演示、测试、截图全得停摆。我的处理是把队列抽象成四个动作：

class EventQueue:
    def publish(self, event_id): ...       # 投递
    def claim(self, consumer, count): ...  # 认领
    def ack(self, event_id): ...           # 确认
    def pending_count(self): ...           # 还有几条没确认

然后写两个实现：

  • DatabaseQueue（默认）：用 delivered / claimed_by / claimed_at 三个字段，在一张 SQLite 表里模拟 Stream 的投递-认领-确认。重复投递就把消息重新置为未确认，于是能被再次认领——正好是 at-least-once 的语义。
  • RedisStreamQueue：XADD 投递、XREADGROUP 认领（先读 Pending 再读新消息 >）、XACK 确认、XPENDING 查积压，一个真实消费组该有的都有。

get_queue() 读环境变量决定用哪个，Redis 连不上就自动回退到数据库队列，并在页面上写明原因。于是：本机零依赖能跑、装了 Redis 一行环境变量就能切、业务代码一行不用改。

为了不让 Redis 那条路径变成「没测过的代码」，我在测试里写了个 FakeRedis：只用几十行实现那六个命令的内存版语义。这样「消费者崩溃没 ACK → 消息重投 → 幂等闸门拦下」这条经典场景，在没有 Redis 的机器上也能被真实断言覆盖。

事后回看，这个「抽象接口 + 自动回退 + 内存替身」的组合，比 Redis 本身更让我有收获：它把一个环境依赖问题，变成了一个设计问题。

五、把抽象的东西变成能看见的东西

后端概念最难受的地方是「看不见」。所以我把整个系统做成了一个演示控制台：五个按钮，点一下真的跑一遍完整链路。

  • 正常流程：四个阶段按序到达
  • 重复投递：同一个 event_id 投三次
  • 乱序投递：倒序投四个阶段
  • 一键跑全部场景 / 清空重来

页面上实时显示：六格统计、订单的位图小方块与进度条、每次消费尝试的时间线（生效 / 重复拦下 / 乱序暂存用不同颜色）、对外通知日志、状态变更流水。三个白话术语卡就摆在顶部——幂等像电梯按钮、乱序是后发的先到、位图是一个数字记进度。

结果第一版就翻车了：「重复拦下」那一格永远显示 0。

查下来不是逻辑错，是被拦下的请求压根没写库——幂等闸门 return 得干脆利落，什么痕迹都没留。测试一断言就露馅了。于是补了第七张…不对，是第六张表 DeliveryAttempt：ProcessedEvent 一个 event_id 只有一条，负责正确性；DeliveryAttempt 来几次记几条，负责可观测性。

这件事给我的印象比幂等本身还深：系统「做对了」和「能证明自己做对了」是两件事。生产环境里后者往往更值钱。

六、怎么证明它真的对

我没有靠肉眼点按钮，而是写了 19 个自动化测试（python manage.py test）：

  • 同一事件投 4 次 → 通知只有 1 条、duplicate_hits == 3、尝试记录 4 条
  • 四个阶段全倒序 → 最终位图 01111、三条暂存全部重放、通知恰好 4 条
  • 已完成后再收到旧事件 → 拒绝且位图不变
  • 完成后想取消 → 拒绝
  • 唯一约束在并发写入下确实抛 IntegrityError
  • 队列认领/ACK、Redis 不可用回退、FakeRedis 的 Pending 重投被幂等拦下
  • 页面 GET 200、按钮 POST 302、GET 访问写接口返回 405

另外 python manage.py demo_notify --scenario mixed 会打印一张真实的事件表。我最喜欢这两行：

bc64e2bf29484810  APPLIED      0 → 15    按序推进；顺带重放 3 条暂存事件
...
对外通知共 12 条（同一 event_id 只会出现一条，重复消费不会重发）

三笔订单全部收敛到 01111，版本都是 4，通知恰好 12 条（3 单 × 4 阶段）。重复投递 5 次，一条多余通知都没发出来。 这比任何解释都有说服力。

七、还踩了几个小坑

顺手记一下，都是真实发生的：

  • 字段名撞车：OneToOneField(event) 在 Django 里自动生成的属性名就是 event_id，我又显式声明了字符串字段 event_id，manage.py check 直接报 models.E006。外键改名 source_event 并指定 db_column 才解决。
  • 暗色主题白底白字：按钮背景硬编码了 #fff，系统切到暗色时文字变浅，截图上几乎看不见。改成 CSS 变量 var(--surface) 后深浅色都正常。
  • 手机端疑似溢出：表格 white-space: nowrap 会把 grid 列撑开。给 .card 加 min-width: 0，再注入脚本对比 scrollWidth 和 innerWidth（489 < 504）确认没有横向溢出。

这几个和幂等都没关系，但确实提醒了我一件事：「功能对」和「能用」之间还隔着一整层细节。

八、做完之后

这个项目最出乎我意料的一点是：它比「闲小集」小得多，但骨架感更强。闲小集是十几个功能在重复同一套「模板 → 路由 → 视图 → 模型」；这个项目只有一条流水线，却把「为什么这么设计」逼了出来——为什么不能用 if、为什么不能丢乱序消息、为什么唯一索引要放在数据库、为什么需要一张只记尝试的审计表。

如果说上一个项目让我认识了流程，这个让我第一次碰到了约束：正确性不是靠写对每一行代码，而是靠把「不许发生的事」交给数据库、交给数学（按位或）、交给事务去保证。

后面还能往下走不少：接真实 Redis 集群做积压监控、幂等键换成业务语义键、加乐观锁做并发压测、失败多次的事件进死信队列。但就现在这一版，我已经能指着看板说清楚：这条通知投了三次，订单没乱，短信只发了一条，而且每一步都有据可查。

对「学一个后端概念」这件事来说，我觉得这比读完一篇讲幂等的文章要扎实一点。
